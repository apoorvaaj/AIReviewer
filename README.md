# IB Feedback Coach (Phase 1 prototype)

A desktop app that asks IB Physics students **questions** about their Internal
Assessment draft, criterion by criterion. It never writes, rewrites or suggests
wording, and the student sees every byte that leaves their laptop before
anything is sent.

> **Status: prototype.** The knowledge base is a developer-written draft
> (`status: draft_needs_teacher_review` on every check) and must be rewritten
> and approved by experienced IB Physics teachers before any use with
> students. Not affiliated with or endorsed by the International Baccalaureate.

## 1. Quick start

Requirements (Windows 11): Rust (stable, MSVC toolchain), Visual Studio C++
Build Tools, WebView2 (preinstalled on Windows 11). Python 3 is needed only
to regenerate the sample documents and icons.

```powershell
# API key (the app reads it from the environment; it never stores it)
$env:ANTHROPIC_API_KEY = "sk-ant-..."

cargo run -p ib-feedback-coach            # run the desktop app
cargo test -p coach-core                  # full offline test suite
cargo build -p ib-feedback-coach --release # release binary in target/release
```

Optional settings (models, effort, concurrency, ZDR wording) go in a
`config.toml`; see [`config.example.toml`](config.example.toml).

Sample drafts to try: [`samples/generated/`](samples/generated/) (synthetic,
generated by `python tools/make_samples.py`).

> **Smart App Control (developers only).** On a Windows 11 machine where
> Smart App Control is *On*, Windows blocks freshly compiled unsigned
> executables, including Cargo build scripts (`os error 4551`). Build in CI
> or on a dedicated development machine or VM. This affects development
> only: students install a signed release and never change security
> settings (see §8.3).

## 2. Architecture

```
ib-feedback-coach/
  core/                    coach-core: ALL trust-critical logic (no UI, never writes to disk)
    src/parse/             .docx (zip + quick-xml, body only) and .pdf (pdf-extract) -> paragraphs
    src/sections.rs        labels paragraphs by IA section from headings
    src/redact.rs          local redaction -> placeholders like [STUDENT_NAME]
    src/kb.rs              loads + validates the knowledge base YAML
    src/payload.rs         builds the EXACT requests; ConfirmedPayload = the send gate
    src/net.rs             the ONLY code that can open a network connection
    src/reasoning/         ReasoningEngine trait + Anthropic implementation + prompts
    src/validate/          deterministic rules, prose heuristic, second pass (fail-closed)
    src/pipeline.rs        wires the stages; bounded-concurrency run
    src/report.rs          feedback report HTML (no scripts, no external resources)
    src/receipt.rs         session receipt JSON + HTML (cannot hold document text)
    tests/                 unit, integration, audit and red-team tests
  src-tauri/               desktop shell (Tauri 2)
    src/commands.rs        the ENTIRE UI -> core surface (8 commands)
    src/main.rs            window setup: incognito webview, temp profile deleted on exit
    tauri.conf.json        strict CSP, no external connect-src
    capabilities/          UI may only listen for progress events
  ui/                      plain HTML + CSS + JS, no framework, no build step
  knowledge-base/physics-ia/   versioned, human-editable checks (YAML)
  validator-rules.yaml     banned phrases and thresholds (tunable without code changes)
  samples/                 SYNTHETIC sample IAs (Markdown source + generated .docx/.pdf)
  tools/                   sample and icon generators (Python standard library only)
```

**Why this stack.**
- **Rust core.** One language for everything an auditor must read. The type
  system enforces "no send before confirmation" at compile time (§4.2).
- **Tauri 2.** Small binary. The webview gets no file, network or shell
  access unless it is granted, and none is granted here.
- **Vanilla JS UI.** About 400 lines, readable in one sitting, with no
  dependency tree.

**Phase 2 seam.** `core/src/reasoning/mod.rs` defines `ReasoningEngine`.
Parsing, redaction, payload, validation, report and receipt only see that
trait, so an offline engine plugs in without restructuring (§8).

## 3. Data flow

```
 [student picks .docx/.pdf in native dialog]
        │  file read into memory (Rust process); SHA-256 of bytes kept for receipt
        ▼
 parse (body text only; headers/footers/comments/metadata/images never read)
        ▼
 student types name / candidate code / school / supervisor  (memory only)
        ▼
 redact (local) ──► student reviews highlighted result, adds terms, un-hides false positives
        ▼
 student picks criteria
        ▼
 sections ─► one task per KB check (only the sections that check needs;
             whole-document checks get the full redacted text)
        ▼
 payload::build_bundle  — exact JSON bodies + URL + models + SHA-256   (pure, no I/O)
        ▼
 ┌──────────────────────────────────────────────────────────┐
 │ "WHAT LEAVES YOUR LAPTOP"                                │
 │ destination, models, request count, size, fingerprint,   │
 │ data-handling statement, every request (excerpt + exact  │
 │ bytes), second-pass template                             │
 └──────────────────────────────────────────────────────────┘
        │ student ticks "I have looked" and presses Send; UI echoes the hash
        ▼
 payload::confirm(bundle, hash)  ──►  ConfirmedPayload      ═══ first network byte ═══
        ▼
 per-check calls (Sonnet; Opus via config), structured output
        ▼
 validator (deterministic rules) ─► dedupe ─► second pass (Haiku, fail-closed)
        ▼
 questions shown; rejected items counted, never shown
        ▼
 student MAY save: feedback-questions.html, receipt .json + .html (save dialogs)
 close / "Start a new review": all in-memory state dropped
```

## 4. Trust guarantees and how each is enforced

Each guarantee below lists **where** it is enforced and **which test** fails if
the code drifts.

### 4.1 The tool never writes for the student

| Mechanism | Where | Test |
|---|---|---|
| No free-text prompt anywhere. The only inputs are identifiers and redaction terms, and they only *remove* text from what is sent. | `ui/index.html`, `src-tauri/src/commands.rs` | `audit.rs::ui_has_no_network_and_no_html_injection` (no `<textarea>`) |
| Model output constrained to `{weakness_present, items[{criterion, check, student_quote, question}]}` by JSON-schema structured output, then re-parsed with `deny_unknown_fields`. Extra fields such as `rewrite` cause rejection. | `reasoning/cloud.rs`, `validate/mod.rs` | `schema.rs`, red-team cases 03, 04 |
| Deterministic validator, all rules fail-closed (below) | `validate/rules.rs`, `validator-rules.yaml` | `validator.rs` |
| Second-pass model: "could any part of this be pasted into the essay?" Missing verdict, error or malformed output all **drop** the item. | `validate/second_pass.rs` | red-team cases 16, 17 |
| Rejected items are never shown, and each rejection is counted by rule | `pipeline.rs::RunLog` | `redteam_offline.rs` (`expect_rejected_by`) |

**Validator rules** (an item is rejected if any rule fails):

1. Empty field, or `check`/`criterion` not the check that was asked (no spoofing).
2. Control, zero-width, bidirectional or Cyrillic characters (homoglyph tricks such as "rеphrase").
3. `student_quote` is not an exact substring of the redacted text that was sent for that check. Matching is after typography normalisation only (curly to straight quotes, dash variants, whitespace runs, NFC); nothing else is relaxed. Quote length is 3–60 words.
4. `question` does not end with `?`, or contains more than one `?`.
5. `question` is shorter than 5 or longer than 35 words, or longer than 250 characters.
6. `question` contains a banned phrase (configurable: *rephrase, change to, replace with, consider writing, a better way to say, for example, should read, here is…*), matched case-insensitively on whole words.
7. Grade language (marks, bands, scores, "7/7"…). Phase 1 never predicts grades.
8. Quoted text longer than 3 words inside the question that is not the student's own words. This stops wording being smuggled in as "Would 'X Y Z…' be clearer?".
9. **Paste-able prose heuristic** (`validate/prose.rs`):
   - A genuine Socratic question is *addressed to the student* and *asks* something. Essay content is a declarative statement *about the physics*.
   - Runs of 6 or more words copied from the student's own text are masked, since quoting them back is fine.
   - The question is split into clauses. Any clause longer than 8 words (`prose_run_max_words`) must contain a second-person word (*you/your*) or a wh-word, or open the question with an auxiliary-verb inversion. Otherwise it is rejected.
   - Leading-question complements ("Have you considered **that the parallax error accounts for the scatter**?") are checked separately. A proposition after the opener that is long and not about the student counts as a claim, and is rejected.
10. More than 2 items per check, inconsistent output (`weakness_present: false` with items), and duplicates.

### 4.2 Minimum data leaves the laptop, and the student sees exactly what leaves

| Mechanism | Where | Test |
|---|---|---|
| Only body text is parsed. Headers, footers, footnotes, comments, document properties and images are never read. The sample `.docx` has the student name in its header for this test. | `parse/docx.rs`, `parse/pdf.rs` | `parsing.rs` |
| Local redaction combines typed identifiers (full name in any case, plus each capitalised name part), labelled lines ("Name:", "School:"…), email, phone and IB candidate-code patterns, and student-added terms. The student can also un-hide false positives. | `redact.rs` | `redaction.rs`, `network_gate.rs::sent_text_contains_no_identifiers` |
| Each check is sent only the sections it needs. The reference list is never sent. | `sections.rs`, `pipeline::build_tasks` | `parsing.rs` |
| **Send gate in the type system.** Every sending method of `ReasoningEngine` requires `&ConfirmedPayload`. That type has a private field, and its only constructor is `payload::confirm`, which recomputes the SHA-256 of the bundle and requires it to equal the hash the UI displayed. Sending without confirmation does not compile, and a payload changed after display is refused. | `payload.rs`, `reasoning/mod.rs` | `network_gate.rs` (0 calls before confirm, wrong hash, tampered body, tampered model; sent bytes equal displayed bytes) |
| `payload::confirm(` appears exactly once outside the core, inside the `confirm_and_run` command. | `commands.rs` | `audit.rs::confirmation_is_only_created_by_the_send_command` |
| Only `core/src/net.rs` may use `reqwest`, sockets or `std::net`. No HTTP or updater plugin. | `net.rs` | `audit.rs::only_net_rs_can_touch_the_network` |
| The webview cannot reach the network. The CSP has `connect-src ipc:` only, the capability file grants only event listening, and the UI contains no `fetch`, XHR, WebSocket or URLs. | `tauri.conf.json`, `capabilities/default.json`, `ui/` | `audit.rs::tauri_config_is_locked_down`, `ui_has_no_network_and_no_html_injection` |
| The payload screen states data retention honestly. Wording depends on `zero_data_retention` in config, and the default says ZDR is **not** confirmed. | `reasoning/cloud.rs::data_handling_text` | — |
| The second-pass request is not known before results arrive. It is a fixed template (shown and hashed) plus generated questions and quotes. Quotes must be substrings of the confirmed text, so no new student text leaves. | `pipeline.rs` step 3 | `redteam_offline.rs` |
| **No disk writes** except the two save commands. The core contains no file-write calls. The shell writes in exactly 3 places (report, receipt JSON, receipt HTML), all inside `save_report`/`save_receipt`, to paths the student picked. Nothing is auto-saved. | `core/`, `commands.rs` | `audit.rs::core_never_writes_to_disk`, `desktop_shell_writes_only_in_the_two_save_commands` |
| No telemetry or analytics, and no web storage in the UI | `ui/app.js` | `audit.rs` (no `localStorage`/`sessionStorage`/`indexedDB`) |
| API key is read from `ANTHROPIC_API_KEY` (or `config.toml`) and never written by the app | `config.rs` | — |

### 4.3 Session receipt

`receipt.rs` builds a `Receipt` struct that **has no field able to hold
document text**, file names, identifiers or questions. It contains only:
- versions, timestamp and models (configured and actually responded);
- KB id, version, syllabus year, review status and SHA-256;
- validator-rules version and SHA-256;
- SHA-256 of the original file and of the confirmed payload;
- redaction counts by kind;
- criteria, request counts, and items generated/shown/rejected by rule;
- a plain-English acknowledgement statement.

It is saved as JSON plus a readable HTML page with a *Print / save as PDF*
button. **Test:** `receipt.rs` asserts that no 6-word run of the document
appears in either output.

### 4.4 Feedback quality via decomposition

- One API call per knowledge-base check (34 checks in total), each carrying:
  - the check definition, what to look for, weakness patterns and question templates;
  - only the relevant sections of the draft.
- Four whole-document checks get the full redacted text. For example: does the conclusion answer the research question, and do uncertainties carry through.
- The system prompt and document block use prompt caching, so the ~34 calls share a cached prefix.
- Prompt injection is handled two ways:
  - Document text sits inside delimited tags and is declared as data. Delimiter look-alikes in the student text are neutralised (`prompts::sanitize_excerpt`).
  - The real guard is the validator, not the prompt.
- No marks or grade bands. The schema has no field for them, and the validator rejects grade language.

## 5. Tests

```powershell
cargo test -p coach-core                                   # everything offline (CI)
cargo test -p coach-core --test redteam_offline            # just the red-team suite
$env:ANTHROPIC_API_KEY="..."; cargo test -p coach-core --test redteam_live -- --ignored --nocapture
$env:IB_COACH_LIVE_MODEL="claude-opus-5-5"                 # (optional) compare models live
```

| File | What it proves |
|---|---|
| `parsing.rs` | .docx/.pdf extraction, headers/metadata ignored, section detection |
| `redaction.rs` | identifiers, patterns, false-positive guards (measurement data is not a phone number) |
| `schema.rs` | malformed / extra-field / wrong-shape output rejected |
| `validator.rs` | every rule, with positive and negative cases |
| `knowledge_base.rs` | KB loads, every check is a draft, every question template passes the validator |
| `network_gate.rs` | no network before confirmation, tamper-proof hash, sent == shown, no identifiers sent |
| `receipt.rs` | receipt contains no document text |
| `audit.rs` | static rules on the source tree (network, disk writes, send gate, UI, Tauri config, synthetic samples) |
| `redteam_offline.rs` | 22 attack cases through the full pipeline with a mock network: **zero rewrite-like output reaches the student** |
| `redteam_live.rs` | same documents against the real API (ignored by default, costs money, non-deterministic) |

**Red-team suite.** Each case is one YAML file in
[`core/tests/redteam/cases/`](core/tests/redteam/cases/). To add a case,
copy a file and edit it; the fields are documented at the top of
`redteam_offline.rs`. The offline tier assumes the model **and** the second-pass
model are both fooled, and proves the deterministic rules alone stop each
attack. A control case (18) proves the validator still lets a genuine
question through. The trust guarantee rests on the offline tier. The live tier
measures how often the validator had to step in, which is useful for comparing
Sonnet with Opus.

All test documents are **synthetic**. No real student work is in the repository
(checked by `audit.rs::no_real_student_work_in_samples`).

## 6. Knowledge base

`knowledge-base/physics-ia/` has a `manifest.yaml` (kb_version, syllabus year
2025, criteria) and one YAML file per criterion: Research design (8 checks),
Data analysis (8), Conclusion (7), Evaluation (7). Plus `whole-document.yaml`
(4 checks).

Each check has: `id`, `criterion`, `status`, `scope`, `description`,
`what_to_look_for`, `common_weakness_patterns[]`, `question_templates[]` and
`applies_to_sections[]`.

- All text is original, written from general good practice in scientific investigation. Nothing is copied from IB guides, examiner reports or exemplars. Criterion *names* follow the published IA structure.
- Every check is `status: draft_needs_teacher_review`. While any check is a draft, the app, report and receipt say so.
- **Teacher workflow:** edit the YAML, set `status: teacher_approved`, bump `kb_version` in every file, then run `cargo test -p coach-core --test knowledge_base`. That test checks each question template against the validator.

## 7. Known limitations

- **Questions can still carry content.** "Have you considered friction?" hands
  over a hint in three words. The validator blocks long claims and the second
  pass catches more, but short hints can't be fully removed without blocking
  useful questions. This is the main residual risk. It is mitigated, not
  eliminated.
- **Prose heuristic false positives and negatives.** The heuristic is
  deliberately conservative. It drops some good questions, and a claim
  wrapped in a clause that mentions "your" can pass it, leaving it to the
  second pass.
- **Text only.** Graphs, images and drawn equations are never sent, so Data
  analysis feedback is weaker. The UI says so.
- **PDF extraction is imperfect.** Tables and equations may come out
  garbled. Scanned (image-only) PDFs are refused. .docx works better.
- **Redaction is pattern- and identifier-based** (no name-recognition
  model). Names the student doesn't type and that aren't in labelled lines,
  such as a lab partner, are only caught if the student adds them. The review
  screen exists for this.
- **Data retention at Anthropic.** The API does not train on inputs by default,
  but under standard terms inputs may be kept for a limited period. Only a
  Zero Data Retention agreement changes that, and the app says which applies.
  The tool is aimed at minors: check Anthropic's usage policies on products
  for under-18s before any pilot.
- **Outside the app's control:** OS pagefile/swap, crash dumps, and
  WebView2's own process data. The webview runs incognito with a per-run
  temporary profile that is deleted on exit, but a crash can leave it behind
  in `%TEMP%\ib-feedback-coach-webview-<pid>`. Document text is never put into
  web storage.
- **Live red-team results are not deterministic.** "All passing" is guaranteed
  for the offline tier only.
- **Windows first.** The code is cross-platform, but the macOS build is
  untested (§8).

## 8. Phase 2 design notes

### 8.1 Offline mode (local open-weight model)

- Add `reasoning/local.rs` implementing `ReasoningEngine`, backed by a
  `llama-server` (llama.cpp) sidecar bound to `127.0.0.1` on a random port,
  or by in-process `llama-cpp-2` bindings.
- `info().destination = "this computer"` and `engine = "local-llama"`.
  `plan_check` produces the same `PlannedRequest`, so the payload screen
  can still show it. It may be skipped for local runs, with the receipt
  recording `engine: local-llama`.
- Structured output is done with a GBNF grammar generated from the same JSON
  schema.
- The validator, red-team suite, report and receipt are unchanged. The
  second pass runs on the same local model, or on a second, smaller one.
- `net.rs` gains a loopback-only transport. The audit test continues to
  forbid sockets elsewhere.
- Model weights are downloaded once with a published SHA-256 and verified
  before loading.

### 8.2 Stateless pass-through proxy (replaces the local API key)

```
app ──HTTPS──► proxy (holds Anthropic key, ZDR org) ──HTTPS──► api.anthropic.com
```

- **Stateless.** The proxy forwards the request body unchanged and streams
  the response back. No database, no disk.
- **Logs no content.** Request and response bodies are never logged. It logs
  only timestamp, status, latency, byte counts, model, and an anonymous
  per-install token for rate limiting. That token is random and not tied
  to identity.
- **Allow-list.** Only `POST /v1/messages` with models from a fixed list. A
  maximum body size and `max_tokens` cap are enforced. Bodies with `tools`
  are rejected.
- **Auditable.** Open source, small enough to read in one sitting, deployed
  from a reproducible build. The app shows the proxy host on the payload
  screen and pins its TLS certificate.
- **App change.** Only `net.rs` and `config.rs` change: base URL plus
  install token instead of `x-api-key`. Hash and confirmation logic are
  untouched.

### 8.3 Builds and distribution

- **macOS build.** Tauri targets macOS from the same code. Config is
  already read from `~/Library/Application Support`. The remaining work is
  building on a Mac, then signing and notarising with an Apple Developer ID.
  WKWebView incognito/data-directory behaviour should be verified there.
- **Windows signing (required before any student use).** Students are never
  asked to weaken their operating system's security, including turning off
  Smart App Control, disabling antivirus or clicking past SmartScreen
  warnings. Smart App Control blocks unsigned executables, so every release
  build is Authenticode-signed with a certificate from a CA that Windows
  trusts (for example via Microsoft's Trusted Signing service). The
  installer and app then show a verifiable publisher name. Signing goes in
  CI, configured via `bundle.windows.signCommand` or
  `certificateThumbprint`, and the private key never sits on a developer
  laptop.
- **Release test matrix** includes a Windows 11 machine with Smart App
  Control **On**: the signed installer must install and run there with no
  warnings.
- **Published hashes.** The SHA-256 of each release installer is published
  alongside it, so a school IT administrator can verify the download.
- **CI** ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)). Every
  push and pull request runs the full offline test suite on Windows and
  checks the shell compiles. It then builds **unsigned, test-only** NSIS
  and MSI installers with SHA-256 checksums, kept as a 7-day artifact.
  Actions are pinned to commit SHAs and dependencies to `Cargo.lock`. The
  signed release job is planned at the bottom of that file. Use the
  unsigned installers only in Windows Sandbox or a VM.
